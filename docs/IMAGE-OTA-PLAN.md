# 系统镜像级 OTA：约束与选项（决策待 owner）

状态：**未实现，未决策**。本文只整理已验证的事实约束与三条可行路线的代价，
不替 owner 拍板；在看守原则改变之前，任何脚本都不会自动刷分区。

## 已验证的事实约束

- 根文件系统是**单一 rootfs 分区**（LABEL=rootfs，约 3.1 GiB eMMC），没有
  A/B 槽位；boot 分区是 Android v0 boot 镜像，r138 起由已验证内核制品重打。
  系统分区的写入方式是 EDL（9008），现有验收流程都走它（HARDWARE-R138.md）。
- 仓库看守原则（README"重要的设备边界"）：**本项目脚本不自动刷分区、不重分
  区、不格式化设备**。任何在设备上自动改写 rootfs/boot 的方案都直接触碰这条。
- 已有的 OTA 基础设施只覆盖 Agent 二进制：Ed25519（可选 ML-DSA 双签）、仓库
  外签名、设备侧校验、确认窗口、自动回滚、Factory 版本下限（RELEASING.md）。
  它**不替换** Factory Agent、内核、rootfs 或基带固件；发布公钥文件只能随系
  统镜像到达设备（KEY-MANAGEMENT.md），所以密钥轮换同样卡在镜像更新这一步。
- 持久集（rootfs 重刷后必须有意决定去留的内容）：设备身份与配对状态、
  `/etc/nassimhub/system-admin/`（账户侧公钥、SSH 配置、主机密钥）、第三方程
  序单元与 `/var/lib/nassimhub-programs/`、journald 上限内的历史日志。今天
  的 rootfs 构建不携带其中任何一项，也没有"重刷前导出/重刷后恢复"的工具。
- 内核与模块按 SHA-256 + vermagic 与镜像锁绑定；boot 与 rootfs 必须同版本
  构建来源（ROOTFS-BUILD.md），镜像级 OTA 的载荷至少是（boot 镜像 + rootfs
  tar）成对分发与成对校验。

## 三条路线

### A：A/B 双 rootfs 槽（自动回滚最干净，一次性侵入最深）

一次性把 eMMC 重划为 rootfs_a/rootfs_b + 保持持久集在独立分区。升级写备用
槽、改 boot 的 root= 选择、启动失败回落。代价：重分区违反看守原则，需要
owner 明确批准一次性迁移工具；3.1 GiB eMMC 对半分后每槽约 1.4 GiB，通用
镜像的空间预算要重做；GPT 变更使旧设备的恢复流程全部重写。

### B：维护启动内更新（不改分区表，自动化程度居中）

升级包（boot+rootfs tar+签名）先由 Agent 下载暂存到持久分区；下一次维护启
动（initramfs 或一个专用 maintenance target）里校验签名、重写 rootfs 与
boot，成功后以新 boot 引导一次"验收启动"，通过才保留，失败由 initramfs 用
暂存的旧镜像回写。代价：initramfs 需要扩展（现在只做 LABEL 解析）；
"脚本自动刷分区"的边界仍被触碰，只是限定在维护模式；断电窗口的回写路径
必须真机反复验证。

### C：承认镜像更新走 EDL/重刷，先把"保留集"工具化（最贴合现状）

镜像级更新保持今天的人工 EDL 流程，把自动化投入在做对齐：一个
`backup-retention` 工具在重刷前导出持久集（身份、系统管理配置、程序单元与
数据），一个对应导入工具在新 rootfs 首启后恢复并核对设备身份未变；再配
逐台的刷机报告。代价：不解决"远程批量升级"；收益是不动看守原则、每一步
可人工核验，且它是 A/B 任一方案的必要前置（保留集工具无论选哪条路都要）。

## 建议的推进顺序（若 owner 认可）

1. 先做路线 C 的保留集导出/导入工具（离线可测：假根目录 + 权限/属主断言，
   与 systemadmin 测试同套路），它同时完成 SERVER-MODE-PLAN 第二优先级里
   "rootfs 更新前逐台备份，明确哪些数据会被保留"。
2. 在 1 的基础上给 A、B 各写一份真机验证清单（断电点、回滚点、身份保持、
   板型锁定），由 owner 决定是否批准重分区或维护启动。
3. 密钥轮换依赖镜像路径：无论 A/B/C，公钥文件随新镜像到达设备的现状先在
   文档里与所选路线对齐，避免实现后才发现轮换闭环缺失。
